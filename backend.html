The Backend

Developer documentation for the Social Media Review tool: what runs where, how content and feedback flow, and every command that drives the pipeline. This page is a static part of the app — nothing here reads or writes data.

1What this is

A no-login review tool for social content libraries — built first for the JFCS / Bayit Ba'Valley 100-carousel library, generic by design (board = client). Reviewers open one secret capability URL and vote, pin comments onto slides, propose text and design edits with a pixel-true live preview, upload photos, build new posts from the studio's templates, and queue approved posts for publishing. Everything they do flows back to the content factory as structured, fenced feedback briefs. The app is static files with no build step; a handful of local Node scripts move content in and feedback out.

4The data model

Eight tables, all prefixed sm_, all defined in schema.sql (idempotent — safe to re-run):

TableOne line
sm_boardsOne row per review board; board_key is the secret UUID capability. Provisioned service-role only — anon can read only its own row.
sm_postsOne row per carousel: category, Hebrew title, caption, stage, origin (factory | builder), asset_prefix into storage — and the full source slides JSON.
sm_votesAppend-only yes / no / maybe + a reason; the newest row per (post, author) is that person's vote.
sm_pinsA comment anchored to a point on a slide (0-based slide index, fractional x,y); status open / resolved; the one table with anon DELETE (mistake-fixing).
sm_repliesThreaded under a pin; append-only.
sm_editsThe audit/learning log: every direct edit lands as a row with field (caption, title, slides.<i>.<var>, or slides.<i>.design), exact old→new, status applied. Legacy proposal rows keep their proposed/accepted/rejected statuses.
sm_photosReviewer upload metadata; the bytes live in the sm-photos bucket (public read, image-only anon inserts ≤ 8 MB, path-scoped to boards/<board-key>/…).
sm_publishThe publish queue: channel instagram / facebook / both, status queued / published / failed / canceled, scheduled_for, and a result jsonb the publisher fills in.

Three principles the whole model hangs on

  • The board key is the capability. The link IS the password. Every request carries an x-board-key header and RLS scopes every row to it. No login, ever; the browser holds only the publishable key.
  • Feedback is append-only. Changing your vote = inserting a new row (latest per author wins). Post slides are the one deliberate exception (v1.5): reviewers write them directly, and every write leaves an applied sm_edits audit row — so the record of who changed what survives even though the slides themselves are live.
  • Posts carry their source slides JSON — the same JSON the studio renders from. That single decision enables the live edit preview, the in-app builder, and factory rebuilds from feedback.

5Where edited files are stored

Reviewer edits write directly into the shared post (v1.5): every committed change — in-place text, side-panel fields, design mutations — PATCHes sm_posts.slides, so all devices see it live. Each write also inserts an sm_edits audit row (field, exact old_text/new_text, status applied) — the read-only «היסטוריית עריכות» list and the learning loop feed on it. One edit, end to end:

  1. A reviewer edits a slide's text (or its design) on post.html. The app saves the change into sm_posts.slides for everyone («נשמר לכולם ✓») and logs an sm_edits row: field: "slides.2.p1", old_text, new_text, status applied. Concurrent edits are guarded optimistically: a save that lost the race re-fetches, re-applies on top, and saves again.
  2. On the operator's machine: 
    node scripts/apply-edits.mjs            # --from-board (default): board slides → next version
node scripts/apply-edits.mjs --dry-run  # show what would change, write nothing
node scripts/apply-edits.mjs --replay   # legacy: replay individual accepted edit rows
    The default mode compares each factory post's board slides against the studio's highest content/<id>[.vN].json (canonical JSON); when they differ it writes content/<id>.v<N+1>.json carrying the board's slides verbatim — a new file in the studio, never overwriting an existing version.
  3. Re-render just the changed posts, from the studio dir: 
    node render.mjs --only <id>
  4. Refresh the board: 
    node scripts/ingest.mjs --update && node scripts/go-live.mjs
    Reviewers now see the new version; their votes, pins, and stages survive.

The caption exception

Captions are the one field applied immediately: the app writes straight to sm_posts.caption and inserts an sm_edits audit row (field: "caption", status: "applied"). apply-edits.mjs later reconciles those live captions back into the studio's source of truth, content/captions/<cat>.json — the one place this tool is allowed to write inside the studio.

Design overrides ride the same path

The direct-manipulation editor (fonts, sizes, palette colors, drag offsets, illustration/photo extras, backgrounds) writes slide.design into the shared slides like any other change, and its audit row uses field: "slides.<i>.design" with the whole design object as canonical JSON ('' means deleted). Since the board slides travel verbatim in --from-board, designs need no special handling on intake. The invariant: compose.js in the browser and the studio's render.mjs apply design identically, so what previews in the app is what the final PNG shows.

6Adding new posts

Route A — AI / factory posts (the main road)

A factory session drops a content JSON into the studio, renders it, and the next ingest picks it up automatically. ingest.mjs scans studio/content/*.json, groups by base id, and publishes each post's highest version that has renders in studio/out/png/ (a JSON with no matching PNGs is reported as a problem and skipped).

Id conventions (they drive categorization):

  • par / cpl / rel / fam / ind prefixes → הורות / זוגיות / רילוקיישן / משפחה / טיפול פרטני (e.g. par01-bedtime-hour)
  • svc* ids and the five intro posts (p10-what-is-bayit, p11–p14-intro-*) → הכירות (meet)
  • other p-series originals → ליבה (orig)
  • versions are sibling files: <id>.v2.json, <id>.v3.json, … with renders named <id>-v2-01.png, -02.png, …

A minimal content JSON (studio/content/par26-example.json):

{
  "id": "par26-example",
  "title": "Internal English working title",
  "slides": [
    { "template": "cover-ill",
      "vars": { "kicker": "…", "display": "כותרת בעברית", "ill": "lamp-table" } },
    { "template": "essay",
      "vars": { "eyebrow": "…", "p1": "…", "p2": "…", "p3": "…",
                "mark": "…", "ill": "clock-face" } }
  ]
}

Then:

# in the studio dir:
node render.mjs --only par26-example
# back in the tool root:
node scripts/ingest.mjs --update && node scripts/go-live.mjs

Route B — the in-app builder

Reviewers build posts on build.html: pick a curated template, fill the fields, watch it compose live, save. That inserts an sm_posts row with origin: "builder", category builder, and an empty asset_prefix — the post has no PNGs, only its slides JSON, and displays compose-only until a factory session adopts it into the studio (writes the content JSON, renders it, re-ingests). Builder posts can't be published before that — publish-meta.mjs refuses posts without public renders.

Route C — captions

Captions live per category in studio/content/captions/<cat>.json (par.json, cpl.json, rel.json, fam.json, ind.json, meet.json, orig.json) as a flat { "<base-id>": "caption…" } map. Ingest attaches them to posts by base id; in-app caption edits flow back per section 5.

What works today once tokens land: Facebook-only publishing (channel: facebook in the queue) — the Page is real. Instagram unlocks the moment the account is created and linked. A dev-mode Meta app can publish to accounts whose admins have a role on the app — no App Review needed for the trial runs.

Why Graph API direct, not Hootsuite

Hootsuite's bulk composer can't schedule carousels (text + one image only) — and this library is ~100 carousel posts. The Graph API publishes carousels natively from public image URLs, which the sm-assets bucket already serves. Hootsuite stays as a manual fallback for one-offs.

One-time setup planned — waiting on account access

  1. Create a Business app at developers.facebook.com.
  2. IG account must be Professional and linked to the FB Page.
  3. Permissions: instagram_basic, instagram_content_publish, pages_manage_posts, pages_read_engagement, business_management.
  4. Exchange a short-lived Graph Explorer token for a long-lived (~60-day) token; fetch the IG user id via GET /<PAGE_ID>?fields=instagram_business_account.
  5. Values go in .env only: META_IG_USER_ID, META_PAGE_ID, META_ACCESS_TOKEN.

The flow (built and dry-run testable today)

node scripts/publish-meta.mjs            # DRY RUN — prints the exact plan, posts nothing
node scripts/publish-meta.mjs --live     # actually publishes, updates the queue rows

IG carousels: one POST /{ig}/media per slide, a CAROUSEL_ALBUM container, poll until FINISHED, then media_publish. FB: unpublished Page photos + attached_media on /feed. Guardrails: the script stops after 20 IG publishes per run (IG allows ~50/24h); trial batches stay ≤ 10/day; scheduled_for rows wait until their time; the ~60-day token expiry shows up as every row failing with an OAuth error. No Stories, no TikTok/LinkedIn through this pipeline.

8Git & repos

  • Current state: only app/ is a git repo, pushed to the public Pages repo yoniversefilms/social-media-review. That's safe by construction: the app holds tool code and the publishable key only — no client content, no secrets.
  • Recommended planned: make the tool root a git repo pushed to a private repo, so scripts, schema, and docs get history too. The root .gitignore already excludes .env, node_modules/, assets-local/, and *.local.json.
  • Separate concern: the studio and all content JSONs live in the client project (Claude_JFCS), not here.
  • Never committed, anywhere: .env (secret key + Meta tokens), board keys in docs or code, and assets-local/ (client renders on disk).

9Runbook

All commands run from the tool root (~/Documents/social media review) unless noted.

CommandWhen to run it
node scripts/ingest.mjs --local Fresh local board build from the studio (first run, or when you want a clean slate — resets local feedback state).
node scripts/ingest.mjs --update Refresh posts / captions / assets from the studio, preserving feedback and stages. Run after any studio change.
node scripts/serve.mjs Local dev server on port 8907: the app + assets + the /api backend (state in assets-local/state.json).
apply schema.sql done 2026-07-31 Operator-run, once (idempotent — re-run when schema.sql changes): Management-API curl per docs/SETUP.md §1, or dashboard SQL editor paste.
node scripts/go-live.mjs (--dry-run) Provision the board (secret UUID key), upload assets to sm-assets, seed sm_posts. Idempotent; re-run after every ingest --update. Prints the real board key and the reviewer URL.
node scripts/apply-edits.mjs (--replay · --all · --local · --dry-run) Default --from-board: posts whose board slides differ from the studio's latest version become the next studio content versions (--replay = legacy per-row replay). Then render → ingest → go-live.
node scripts/sync.mjs (--local) Pull all boards' feedback into fenced factory briefs at New_Workflow/feedback/<date>/. Weekly, or before any factory session.
node scripts/publish-meta.mjs (--live · --post <id> · --include-future · --local · --assume-public) Consume queued sm_publish rows. Dry-run by default; --live only on the operator's say-so.
node render.mjs (--only <substr> · --templates · --content) Studio renderer — run inside the studio dir (../Claude_JFCS/New_Workflow/studio) after content changes.
